# Field encryption and work authorization (Phase 3)

Migration 0042. Design references: A6.3 (field encryption, blind index), B2.4
(`work_authorization`), B4.4, B4.6, B6 (`key-rotation`, `visa-expiry`),
FR-VIS-01 to 03, FR-NTF-11. JSON, RFC 9457 problems with the code in `detail`,
CSRF header on writes.

## Field encryption platform

| ID | Rule |
|---|---|
| FE-1 | Envelope encryption: AES-256-GCM under a per-class data key (`work_auth_number`, `dob`). Data keys are generated by KMS (`FIELD_KMS_KEY_ARN`, the restricted key) with the encryption context `{eureka:purpose: field, eureka:field-class, eureka:key-id}` and stored only wrapped in `eureka.field_key` (id, class, version, provider, key_ref, wrapped_key, rotation_key). Unwrapped keys are cached in process memory for up to 24 hours. |
| FE-2 | Ciphertext: `0x01 \| key id (16) \| key version (uint32 BE) \| IV (12) \| ciphertext \| tag (16)`. The AAD is the header plus `table`, `column` and the row id, so a value moved to another row, column or table, or with any byte changed, fails. The table CHECKs that the header's key id equals the key column. |
| FE-3 | The API adds a class's first key on first use (`authz.field_key_first`, refuses when one exists); every other key comes from the worker's monthly rotation (`authz.field_key_rotate`, one per class and UTC month, never in the future). Keys are never changed or deleted (owner and superuser included). |
| FE-4 | Local development and tests use a local provider (AES-GCM key wrap with a development key from the repository, or `FIELD_LOCAL_KEY`). The API and worker refuse to start in production without `FIELD_KMS_KEY_ARN` (and the API without `BIDX_KMS_KEY_ARN`) or with a local key set; the factories refuse the local provider in production too. A data key is only unwrapped by the provider and key that created it. |
| FE-5 | Blind index: `HMAC-SHA256(bidx key, "eureka-bidx:v1\0" + class + "\0" + normalized value)`, 32 bytes. In AWS a separate KMS HMAC key (`BIDX_KMS_KEY_ARN`, GenerateMac only); locally an HMAC key (`BIDX_LOCAL_KEY` or the development key). `normalizeDob` accepts ISO dates only. |
| FE-6 | Plaintext never enters logs, `audit_event`, `outbox_event` or `job_run`; audit redaction also covers `number`, `numberEnc`, `number_enc`. |
| FE-7 | IAM: the API and worker may use the restricted key directly only with `kms:EncryptionContext:eureka:purpose = field`; the API may call `kms:GenerateMac` on the bidx key; the worker has no bidx right. |

### key-rotation job (worker, monthly)

Run key = UTC month (`YYYY-MM`), due on the 1st at 05:00 America/New_York;
a missed month is not caught up (the next month covers it). For each rotated
class (`work_auth_number`; `dob` once DOB is written): add or reuse the month's
key, then read rows not under it in id order (`authz.field_rotation_batch`,
`KEY_ROTATION_BATCH_SIZE`, default 100), decrypt with the row's key, encrypt
with the new key bound to the same row, and swap through
`authz.field_rotation_apply` (only if the row still holds what was read, and
only to the newest, higher key version). `job_run.detail`:
`{ <class>: { keyVersion, reencrypted, skipped, failed } }`. A row that does
not decrypt is counted as `failed`, logged by id with `alert: true` and left
unchanged. Rotation does not change `row_version` or `updated_*`.

## Work authorization

| ID | Rule |
|---|---|
| WA-1 | One row per authorization of a person (candidate or employee; `person_id`): `type`, number (encrypted, optional), `validFrom`, `validTo`, `status` (`pending`, `valid`, `revoked`). `expired` is derived (`validTo` before today's New York date), never stored. Rows are never deleted (revoke instead). |
| WA-2 | Read: `visa:read` covering the owning candidate (ownership, team, hierarchy, location or org, never Open-to-all-teams) and the candidate readable. Today that is HR and Immigration (org). This is stricter than design B4.4 ("document:read scope"), pending a decision (docs/HANDOFF.md). |
| WA-3 | Write: `visa:update` covering the candidate (Immigration), through `authz.work_auth_create` / `authz.work_auth_update`, which re-check scope and permission; the guard trigger sets `created_*`, `updated_*`, `row_version` and refuses deletes, truncation and changes to `id`, `person_id`, `created_*`. |
| WA-4 | The number is never in a list or write response: `numberMasked` is a fixed mask. `POST .../reveal` returns it to `visa:read` holders when the session's sign-in is at most 15 minutes old (step-up; else 403 `step_up_required`), at most 20 per user per minute, audited as `work_authorization.number_revealed` with `{ candidateId }` only. When the shared step-up from restricted documents lands, the reveal should use it. |
| WA-5 | Audit: `work_authorization.created` (`candidateId, type, status, validFrom, validTo, numberSet`), `work_authorization.updated` (changed fields, `numberChanged`, `numberSet`). Never the number. |

### Endpoints

- `GET /api/v1/candidates/:id/work-authorizations` (`visa:read`) returns
  `{ items: [WorkAuthorization], canEdit, canReveal }` (newest expiry first, at most 50).
- `POST /api/v1/candidates/:id/work-authorizations` (`visa:update`) with
  `{ type, status, number?, validFrom?, validTo? }` returns 201 `{ id, rowVersion }`.
- `PATCH /api/v1/candidates/:id/work-authorizations/:waId` (`visa:update`, header
  `If-Match: "<rowVersion>"`; 428 without, 412 `stale` when changed) with any of
  `{ type, status, number, validFrom, validTo }` (`number: null` removes it, omitted keeps it) returns `{ id, rowVersion }`.
- `POST /api/v1/candidates/:id/work-authorizations/:waId/reveal` (`visa:read`, no body) returns `{ id, number }`; 409 `no_number` when none is stored.

`WorkAuthorization` = `{ id, type, numberMasked, hasNumber, validFrom, validTo, status, expired, daysToExpiry, rowVersion, createdAt, updatedAt, updatedBy: {id,name} }`.

Types (`WORK_AUTH_TYPES` in `packages/shared`): `h1b`, `h4_ead`, `l1`, `l2_ead`,
`f1_opt`, `f1_stem_opt`, `f1_cpt`, `gc_ead`, `green_card`, `tn`, `o1`, `other`
(placeholder list until Immigration confirms it). Numbers are normalized
(spaces removed, upper case) and must match `^[A-Z0-9][A-Z0-9-]{0,39}$`.

Errors: 404 when the candidate is not readable or `visa:read` does not cover it;
403 without the permission (guard) or without `visa:update` over the candidate;
422 validation (unknown keys refused, values never echoed).

The web app shows the section on the candidate profile to `visa:read` holders.

## Outbox event `work_authorization.expiring` (for the notification jobs)

Inserted by the worker job `visa-expiry` (daily after 06:00 America/New_York)
through `authz.work_auth_expiry_notices(thresholds)`; thresholds come from
`WORK_AUTH_EXPIRY_NOTICE_DAYS` (default `90,60,30`, 1-10 values of 1-365 days).

```json
{
  "type": "work_authorization.expiring",
  "aggregate_type": "work_authorization",
  "aggregate_id": "<work_authorization.id>",
  "payload": {
    "candidate_id": "<uuid>",
    "person_id": "<uuid>",
    "expires_on": "YYYY-MM-DD",
    "threshold_days": 60,
    "days_left": 58,
    "notify": ["hr", "immigration"]
  }
}
```

- Emitted for records with `status = valid` and `valid_to` between today and
  today + the largest threshold (New York calendar day of the database clock).
- One event per record at the smallest threshold reached: a record entered 20
  days before expiry gets only the 30-day event; a missed day is caught up on
  the next run. Recorded in `work_authorization_notice` (record, threshold,
  expiry date, event id). A notice also covers any earlier expiry date (a
  correction does not repeat it); extending `valid_to` past every noticed date
  (a renewal) starts a new cycle.
- The payload holds ids, the expiry date and day counts only: no number, no
  authorization type, no names. Recipients sign in to see details.
- `notify` (`hr`, `immigration`) is only checked against the type's audience;
  `outbox-delivery` (migration 0046, `docs/notifications.md`) decides the
  recipients (HR and Immigration) and delivers email and an inbox entry.
