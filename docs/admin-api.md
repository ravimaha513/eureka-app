# Admin and team API contract (Phase 1)

Shared contract for the admin backend (`apps/api/src/modules/admin`) and the
Users & Access screens (`apps/web`). JSON over HTTPS. Errors use RFC 9457
problem details. Writes need the session cookie and `x-csrf-token`.

## Decisions and assumptions (least privilege)

| ID | Rule |
|---|---|
| AD-1 | Everything under `/api/v1/admin/*` requires `access:manage` (org scope; only `org_admin` holds it). `org_admin` still has no data permissions. |
| AD-2 | Nobody can change their own roles, status or reporting line (403 `self_change`). |
| AD-3 | Granting a **restricted role** needs a second approver: another `access:manage` holder who is neither the grantee nor the requester, while the grantee is active and the requester is still an admin. Restricted roles: `org_admin`, every role holding a permission in `RESTRICTED_PERMISSIONS` (HR, Accounts, Immigration), and every role holding an org-wide sensitive permission (`ORG_SENSITIVE_PERMISSIONS`: rates, invoices, employees, phones, assignment, team moves, documents), which today adds CEO, BU Head, Associate HR and Documents Team. Other roles apply immediately. |
| AD-3a | Separation of duties: an `org_admin` holds no business role, and a user with a business role cannot be made `org_admin` (422 `separation_of_duties`). Use a separate admin account. |
| AD-3b | **Single-admin mode** (migration 0084): when `SINGLE_ADMIN_MODE=on` is set for the migrate task (Terraform `single_admin_mode`, default `off`), restricted roles apply immediately and the requester may approve a pending request (recorded as `applied`). Self-change, grantee approval, org_admin/data-role separation and audit stay. Stored in `authz.policy_setting single_admin_mode`. |
| AD-4 | Revoking a role, or deactivating a user, is immediate and needs no approval. Least privilege: removing access is never slowed down. |
| AD-5 | Deactivation sets `status = 'inactive'`, ends open role, team, coach and reporting-line rows, closes pending role requests for or by the user, revokes all sessions and bumps `access_version`. It is refused while the user leads a team (`lead_of_team`) or has direct reports (`has_reports`). Reactivation restores the status only. Roles, teams and a manager must be set again. |
| AD-6 | Location-bound roles (`location_incharge`, `location_ops_admin`) require `locationId`; other roles reject it. |
| AD-7 | Every change writes an `audit_event` in the same transaction. Role requests are stored in `role_request` with requester, approver and decision time. A pending request expires after 7 days. |
| AD-8 | Moving a recruiter between teams (OD-07) needs `team:move_member` covering **both** teams in the actor's scope. Their candidates stay with the old team and go to `reassignTo`, which must be an active member or the lead of the old team. It defaults to the old team's lead. It all runs in one transaction in a definer function. |
| AD-9 | Team lead changes and reporting lines are admin-only (`access:manage`) and keep the existing invariants (the closure rebuild and the cycle check). A team member reports to the team's lead (migration 0370, trigger `eureka.team_reporting_sync`): every way into a team (AD-8, AD-10, admin adds, bulk import, org chart) sets the member's reporting line to the lead, and a lead change moves the current members under the new lead. So hierarchy scope (an AD's view of a manager's Hot List and candidates) follows the teams built in the team drawer. Adding someone above the team's lead is 422 `cycle`. Leaving a team keeps the reporting line. |
| AD-10 | Adding people to a team needs `team:add_member`: a lead (`team` scope) adds to the team they lead; a manager or associate director (`hierarchy` scope) adds to any team whose lead is in their reporting subtree. Only active users holding the `recruiter` role and in no team can be added (422 `not_a_recruiter`, 422 `user_inactive`, 409 `already_member`); someone in another team is moved with AD-8. Not yourself. Runs in `authz.team_add_member` (`db/functions/authz/team_add_member.sql`), audited as `team.member_added`. |
| AD-11 | **Interview coaches** support sales teams (`coach_assignment`; the coach sees the team's candidates, Hot List, interviews and training progress, and the team's lead sees their interview feedback through team scope). An `org_admin` (`access:manage`) assigns any active holder of `interview_coach` or `interview_lead` to any team; an **Interview Lead** (`coach:assign`, `hierarchy` scope) assigns the coaches below them in the reporting hierarchy to any team, never themself (403 `self_change`). The Interview Lead reports to the Associate Director and their coaches report to them; their `coached_hierarchy` grants cover the teams coached by them or anyone below them (migration 0220). Not a coach role: 422 `not_a_coach`; already assigned: 409 `already_assigned`; not assigned: 404 `not_assigned`. Runs in `authz.assign_coach` / `authz.unassign_coach` (`db/functions/authz/`, guard `authz.coach_assignment_guard`), audited as `admin.team.coach_assigned` / `admin.team.coach_unassigned` (Users & Access) or `team.coach_assigned` / `team.coach_unassigned` (Interview Lead), `changes: { coachId }` only. |
| AD-12 | Departments (migration 0230) are descriptive: a department and optional sub-department per user (e.g. Sales → Interview Prep), shown and filtered in Users & Access. Only admins (`access:manage`) create, rename or assign them, through definer functions. Nothing in `authz` or any policy reads a department, so it never grants or widens access; scope stays role + reporting line. |
| AD-13 | **Deleting users** (migration 0280). A user inactive for 7 days is deleted by the worker's daily `user-purge-inactive` job (`authz.purge_inactive_users`, audited as `system.user.purged`); an admin can delete a deactivated user sooner (`DELETE /users/:id`). Active users must be deactivated first (422 `user_active`). Deleting anonymizes rather than removes the row, because records (candidates, submissions, chat, audit actors) keep referencing it: email becomes `deleted-<id>@deleted.invalid` (the address is free again), name `Deleted user`, designation, Google link and location are cleared (the department stays: descriptive, AD-12), the password credential is removed and the Settings profile phone, bio and birthday are cleared. Irreversible: a deleted user is 404 for every admin action and never listed. The wait counts from the first deactivation (`deactivated_at`); reactivating clears it. |

| AD-14 | **Removing a team member** leaves them in no team (the membership is ended, not deleted). Allowed for admins (`access:manage`, any team, from the Users & Access team drawer) and for whoever may add to the team under AD-10 (`team:add_member`: the lead, or a manager / associate director above them, from My team). Their candidates on that team go to its lead, as on a move without `reassignTo`; the lead must be active (422 `invalid_reassign_target`). Not yourself (403 `self_change`); someone not in the team is 422 `not_a_member`. Runs in `authz.team_remove_member` (`db/functions/authz/team_remove_member.sql`), audited as `admin.team.member_removed` / `team.member_removed`, `changes: { userId, reassignedTo, movedCandidates }`. |
| AD-15 | **Deleting a team** (`access:manage`, from the team drawer) is soft: the team row stays for history (submissions, interviews, placements, paperwork and job snapshots keep its id and name), gets `deleted_at` and loses its lead (`lead_id` NULL), so it grants no scope, holds nobody as lead (deactivation's `lead_of_team` no longer applies) and disappears from the Teams tab and every team picker. With `toTeamId`, its current members move to that team (and report to its lead, AD-9; 422 `cycle` if that would close a loop) and its candidates go with them: a candidate keeps a recruiter who is now in the target team, otherwise (the old lead) goes to the target's lead. Without it, members are left in no team (reporting line kept, as AD-14) and candidates become "No team yet" (migration 0410) with their recruiter; refused with 422 `has_hotlist_candidates` while any of them is on the Hot List, which is team-owned. Either way coach assignments end and shares to the team are dropped. Moving people under yourself (target led by you) or deleting a team you are a member of is 403 `self_change`; target = the team itself is 422 `same_team`; unknown or already deleted team is 404. Afterwards renames, lead changes, adds, coach assignments and candidates pointing at it are refused as `team_not_found` (`eureka.team_deleted_guard`). Runs in `authz.admin_delete_team` (`db/functions/authz/admin_delete_team.sql`, migration 0430), audited as `admin.team.deleted`, `changes: { toTeamId, members, movedCandidates, unassignedCandidates }`. |

## Endpoints

### Metadata
`GET /api/v1/admin/meta` returns
`{ roles: [{ key, label, restricted, locationBound }], locations: [{ id, name }] }`

### Locations
- `GET /api/v1/admin/locations` returns `{ items: [{ id, name, kind, state, timezone, peopleCount, teamCount, roleHolders: [{ userId, displayName, role, label }] }] }` ordered by name. A location's people are the active users whose primary location it is, who are current members or the lead of a team at it, or who hold a current role for it (`roleHolders`: the location-bound role grants).
- `GET /api/v1/admin/locations/:id` returns `{ location: { id, name, kind, state, timezone }, people: [{ id, displayName, designation, primaryLocation, managerId, roles, teams }], outsideManagers: [{ id, displayName, locationName }], teams: [{ id, name, lead, memberIds, coaches }] }`. `managerId` is the current reporting line; managers who are not themselves people of the location come back in `outsideManagers` so the client can draw the full tree. `teams` are the teams whose location this is. 404 unknown location. Read-only, `access:manage` like the rest of this controller.
- `POST /api/v1/admin/locations` with `{ name, kind, state?, timezone? }` returns 201 `{ id }`. `kind` is one of `training`, `gh`, `office`, `remote`; `timezone` is an IANA name (default `America/New_York`). Only `org_admin` (`access:manage`, org scope) can create one. The write goes through `authz.admin_create_location` (migration 0091) and is audited as `admin.location.created` with `{ kind, fields }` (no name or state, rule 5). A duplicate name is 409 `location_exists`.
- `PATCH /api/v1/admin/locations/:id` with `{ name }` returns 204. Same gate as create; the write goes through `authz.admin_rename_location` (`db/functions/authz/`, column grant in migration 0280) and is audited as `admin.location.renamed` with the id only (no name, rule 5). 404 unknown location, 409 `location_exists`, 422 `invalid_name`. Kind, state and time zone cannot be edited, and locations cannot be deleted, here yet.

### Departments (AD-12)
- `GET /api/v1/admin/departments` returns `{ items: [{ id, name, parentId: uuid|null, userCount }] }` (flat, ordered by name; `userCount` counts active users whose department is exactly this one).
- `POST /api/v1/admin/departments` with `{ name, parentId? }` returns 201 `{ id }`. Two levels only: `parentId` must be a top-level department (422 `invalid_parent`; 404 unknown parent). Names are 1–120 characters, trimmed, no control characters (422 `invalid_name`), unique among siblings ignoring case (409 `department_exists`). `authz.admin_create_department`; audited as `admin.department.created` with `{ parentId }` only.
- `PATCH /api/v1/admin/departments/:id` with `{ name }` returns 204. 404 unknown department. `authz.admin_rename_department`; audited as `admin.department.renamed` without the name.
- `PUT /api/v1/admin/users/:id/department` with `{ departmentId: uuid | null }` returns 204. 404 unknown user or department. Admins may set their own (it grants nothing). `authz.admin_set_user_department`; audited as `admin.user.department` with `{ departmentId, previous }`.
- Departments cannot be deleted or moved yet.

### Users
- `GET /api/v1/admin/users?search=&status=active|inactive&departmentId=<uuid>|none&team=<uuid>|none&role=&locationId=&cursor=&limit=` (default 50, max 200; `departmentId` matches that department and its sub-departments, `none` users without one; `team` the current members of that team, `none` users who neither lead nor belong to a team; `role` holders of that role key; `locationId` the primary location) returns
  `{ items: [{ id, email, displayName, designation, status, primaryLocation: {id,name}|null, department: { id, name, parent: {id,name}|null }|null, manager: {id,displayName}|null, roles: [{ key, label, locationId, locationName }], teams: [{ id, name, asLead: boolean }] }], nextCursor }`
  (interviews-settings, SD-1/ST-3: plus `contactVisible` and, for `staff.contact:read` holders, each item's `phone`).
- `GET /api/v1/admin/users/summary` returns `{ active, inactive, roles: [{ key, label, count }] }`: active users per role, roles with users only (`docs/interviews-settings-api.md` SD-1).
- `POST /api/v1/admin/users` with `{ email, displayName, designation?, primaryLocationId? }` returns 201 `{ id }`. A duplicate email is a 409. The email must be in `GOOGLE_HOSTED_DOMAIN` when that is set (422). Audited as `admin.user.created` with `{ fields, primaryLocationId }` only: names and designations are free text (rule 5, as the rename paths; security review C-05).
- `POST /api/v1/admin/users/bulk` with `{ dryRun, rows: [{ email, displayName, designation?, location?, manager?, team?, roles? }] }` (1 to 500 rows; `location` is a location name, case-insensitive; `manager` is the email of an active user or of another row in the same request; `team` is a team name, case-insensitive, joined as a member; `roles` is up to 5 role keys or labels, case-insensitive) returns 200
  `{ dryRun, committed, created, failed, rows: [{ row, email, displayName, status: "ok" | "error", error?, id?, manager?, team?, roles: [{ role, label, status: "applied" | "pending_approval" }] }] }` (`manager` and `team` are the resolved display names, present when the row names them). All or nothing: one transaction, rolled back when `dryRun` is true or any row fails, so a dry run previews exactly what a real run does, role statuses included (`id` is only present when committed). Row errors: `invalid_email`, `email_domain`, `name_required`, `duplicate_in_file`, `unknown_location`, `email_exists`, `unknown_role`, `duplicate_role`, `separation_of_duties` (Org Admin with another role, AD-3a), `location_required` (a location-bound role without a row location; AD-6: such roles are granted at the row's location). Each user is created by `authz.admin_create_user` and audited as `admin.user.created` (`bulk: true`); each role goes through `authz.request_role` like a single grant and is audited as `admin.role.granted` or `admin.role.requested` (`bulk: true`): restricted roles become pending requests for a second admin (AD-3), unless single-admin mode is on. Managers and teams are set after every row is created, so rows may name each other in any order: all reporting lines in one `authz.admin_bulk_set_managers` call, teams through `authz.admin_add_team_member` (the reporting closure is rebuilt once for the whole pass, team adds included: `authz.reporting_closure_defer` / `authz.reporting_closure_flush`, migration 0476; `access_version` is bumped once per transaction, `eureka.bump_access_version`), audited as `admin.user.manager` / `admin.team.member_added` (`bulk: true`, ids only). Their row errors: `unknown_manager` (no active user and no row with that email), `invalid_manager` (inactive), `manager_row_failed` (the manager's own row failed), `cycle` (oneself, or a loop within the file), `self_change` (the importing admin as manager), `unknown_team`, `ambiguous_team` (team names are not unique; set those in Users & Access). A row's team wins over its manager: the member ends up reporting to the team's lead (AD-9), and a team led by someone below the row is `cycle`. One `admin.user.bulk_created` records the user, role, manager and team counts.
- `GET /api/v1/admin/users/bulk/template` returns the import template as `.xlsx` (`users-import-template.xlsx`): a "Users" sheet with the columns Email, Name, Designation, Location, Manager Email, Team, Role 1-3 for up to 500 rows, Location, Team and Role dropdowns (current location names, team names, role labels) from a hidden "Lists" sheet, and an "Instructions" sheet. The web reads the file in the browser (the "Users" sheet, else the first) and posts rows as above; CSV with the same headers still works.
- `POST /api/v1/admin/users/:id/deactivate` returns 204 (AD-5).
- `POST /api/v1/admin/users/:id/reactivate` returns 204. Clears the deletion wait (AD-13).
- `DELETE /api/v1/admin/users/:id` returns 204 (AD-13): deletes a deactivated user now. 404 unknown or already deleted, 422 `user_active`, 403 `self_change`. `authz.admin_delete_user`; audited as `admin.user.deleted`. Inactive list items carry `deletesAt`, the earliest time the worker deletes them.
- `PUT /api/v1/admin/users/:id/manager` with `{ managerId: uuid | null }` returns 204 (AD-2, AD-9). A cycle is a 422.
- `PUT /api/v1/admin/users/:id/designation` with `{ designation: string | null }` returns 200 `{ id, designation }` (migration 0111; `authz.set_designation`; not yourself; at most 120 characters, no control characters, 422 `invalid_designation`; audited as `user.designation_changed`). Managers and associate directors change designations in their hierarchy through `PUT /api/v1/users/:id/designation` (`designation:change`, `docs/performance-api.md` PF-7).

### Roles
Role definitions (system templates, custom roles, traits, ladders, the permission grid) are in
`docs/roles-api.md`: `GET/POST /admin/roles`, `PATCH /admin/roles/:key`, `PUT /admin/roles/:key/grants`,
`POST /admin/roles/:key/archive|restore`, `GET /admin/permissions`. Grants below accept any live role key.
- `POST /api/v1/admin/role-requests` with `{ userId, role, locationId? }` returns 201 `{ id, status: "applied" | "pending_approval" }`.
- `GET /api/v1/admin/role-requests?status=pending|approved|rejected|expired` returns
  `{ items: [{ id, user: {id,displayName,email}, role, roleLabel, locationId, requestedBy: {id,displayName}, requestedAt, status, decidedBy: {id,displayName}|null, decidedAt }] }`.
  Non-restricted grants are recorded too, with `status: "applied"`; they are listed when no status filter is given.
- `POST /api/v1/admin/role-requests/:id/approve` returns 200 `{ status: "approved" }`. If the approver is the requester or the grantee, the response is 403 `second_approver_required`.
- `POST /api/v1/admin/role-requests/:id/reject` returns 200 `{ status: "rejected" }`.
- `DELETE /api/v1/admin/users/:id/roles/:role?locationId=` returns 204 (AD-4).

### Teams
- `GET /api/v1/admin/teams` returns
  `{ items: [{ id, name, location: {id,name}|null, lead: {id,displayName}, department: { id, name, parent }|null, members: [{ id, displayName }], coaches: [{ id, displayName }] }], coaches: [{ id, displayName, email, role: "interview_coach" | "interview_lead" }] }`
  (`department`: the lead's department, AD-12; top-level `coaches`: the active users who can be assigned as coaches, AD-11; top-level `unassignedCount`: active users who neither lead nor belong to a team).
- `POST /api/v1/admin/teams` with `{ name, leadId, locationId? }` returns 201 `{ id }`. Audited as `admin.team.created` with `{ leadId, locationId }` (no name, rule 5).
- `PATCH /api/v1/admin/teams/:id` with `{ name }` (1–120 chars, trimmed) renames the team and returns 204. 404 unknown team. The audit row (`admin.team.renamed`) does not carry the name.
- `PUT /api/v1/admin/teams/:id/lead` with `{ leadId }` returns 204.
- `POST /api/v1/admin/teams/:id/members` with `{ userId }` returns 204. A user who is already in another team gets a 409; use the move endpoint instead.
- `POST /api/v1/admin/teams/:id/members/bulk` with `{ userIds }` (1–100) returns 200 `{ added: [userId], failed: [{ userId, error }] }`. Each person is added on its own (same function, checks and `admin.team.member_added` audit row as the single add, under a savepoint of one transaction), so one failure does not undo the others; the reporting closure is rebuilt once at the end (0476); `error` is the contract code (`already_member`, `user_inactive`, `self_change`, `user_not_found`, `cycle`). 404 unknown team. Used by the team drawer and the Users tab bulk "Add to team".
- `GET /api/v1/admin/teams/:id/delete-impact` returns `{ members, candidates, hotlistCandidates }` (the delete dialog; 404 unknown or deleted team). `DELETE /api/v1/admin/teams/:id?toTeamId=<uuid>` deletes the team (AD-15) and returns 200 `{ members, movedCandidates, unassignedCandidates }`; omit `toTeamId` to leave its people with no team. 404 unknown team or target, 403 `self_change`, 422 `same_team` / `has_hotlist_candidates` / `cycle`.
- `POST /api/v1/admin/teams/:id/coaches` with `{ userId }` returns 204; `DELETE /api/v1/admin/teams/:id/coaches/:userId` returns 204 (AD-11). 404 unknown team or `not_assigned`, 409 `already_assigned`, 422 `not_a_coach` / `user_inactive`.
- `GET /api/v1/teams/mine` (permission `team:add_member`, AD-10) returns `{ items: [{ id, name, lead: {id,displayName}, members: [{id,displayName}] }], addable: [{ id, displayName, email }] }`: the caller's teams and the active recruiters in no team (for team/hierarchy callers: only those with no manager yet or below the caller, or a lead of one of those teams, in the reporting line).
- `POST /api/v1/teams/:id/members` with `{ userId }` (permission `team:add_member`, AD-10) returns 204. 404 unknown team, 403 `not_in_scope` for a team outside the caller's scope.
- `DELETE /api/v1/admin/teams/:id/members/:userId` (`access:manage`) and `DELETE /api/v1/teams/:id/members/:userId` (permission `team:add_member`, scoped as the add) return 200 `{ movedCandidates, reassignedTo: { id } }` (AD-14). 404 unknown team, 403 `not_in_scope` / `self_change`, 422 `not_a_member` / `invalid_reassign_target`.
- `GET /api/v1/coach-assignments` (permission `coach:assign`, AD-11) returns `{ items: [{ id, name, lead: {id,displayName}, coaches: [{id,displayName}] }], coaches: [{ id, displayName, email, role }] }`: every team, with only the caller's own coaches (active coach-role holders below them) listed on it, and those coaches.
- `POST /api/v1/teams/:id/coaches` with `{ userId }` and `DELETE /api/v1/teams/:id/coaches/:userId` (permission `coach:assign`, AD-11) return 204. 403 `not_in_scope` for someone not below the caller, 403 `self_change` for themself; otherwise as the admin endpoints.
- `POST /api/v1/teams/:id/move-member` with `{ userId, toTeamId, reassignTo? }` (permission `team:move_member`, AD-8) returns 200 `{ movedCandidates: number, reassignedTo: { id, displayName } }`.

- 404: `not_assigned`; 409: `already_assigned`; 422: `not_a_coach` (AD-11)
- 422: `invalid_parent`, `invalid_name`, `invalid_designation`, `email_domain`, `unknown_role`, `invalid_manager`, `invalid_lead`, `user_inactive`, `user_active`, `not_a_member`, `same_team`, `has_hotlist_candidates`, `lead_of_team`, `has_reports`, `separation_of_duties`

## Implementation notes

- Every admin write goes through a SECURITY DEFINER function in `authz` (migration 0013) that re-checks `access:manage`, self-change and the second approver inside the database. `eureka_app` has no write privilege on org tables.
- Self-change (AD-2) also covers changes that would widen the actor's own scope: making someone report to yourself, making yourself a lead, or adding yourself to a team.
- The grantee cannot reject their own pending request; the requester can withdraw theirs.
- `authz.move_team_member` takes the source team too (from the route), so a concurrent move cannot change what is being moved.
- Changing a team's lead moves the old lead's candidates in that team to the new lead (keeps the recruiter/team invariant).
- `DELETE /admin/users/:id/roles/:role` without `locationId` revokes the role at every location.
- Moving members needs `team:move_member`, which `org_admin` does not hold (least privilege: moves reassign candidates, which is business data). The Teams tab shows the action disabled for admins; managers and associate directors will move members from a team view (Phase 2).
- The first admins come from the bootstrap CLI (`authz.bootstrap_admins`, migration 0037; infra/README.md "First admin"), never from the API: break-glass only: it refuses while an active `org_admin` exists (and, after a first bootstrap, without `--recover`), creates two so restricted roles can be approved (AD-3), and is executable only by the migration user.

## Password invite (staging/local, migration 0270)

Only when `PASSWORD_LOGIN=on` (404 otherwise). Instead of choosing a temporary password, an admin emails the user a one-time link.

| Route | Who | Body | Result |
|---|---|---|---|
| `POST /api/v1/admin/users/:id/password-invite` | access:manage, not oneself, active user, no restricted role | none | 204; 403 `restricted_target`/`self_change`; 422 `user_inactive`; 502 `mail_failed` (link stays valid; send again) |
| `POST /api/v1/admin/users` | as create | `sendPasswordInvite: true` (not with `temporaryPassword`, 422 `password_or_invite`) | 201 `{ id, invite: "sent" \| "failed" }` |
| `POST /api/auth/password/setup` | public, rate-limited per IP | `{ token, newPassword }` | 200 `{ mustChangePassword: false }` + session cookie; 400 `invalid_link` (unknown, used, expired, replaced, user inactive or restricted); 422 `password_weak` (link stays open) |

- Link: `${PUBLIC_BASE_URL}/set-password#token=<43 chars base64url>`. The token is in the fragment so it never reaches server or proxy logs; the page clears it from the address bar.
- Stored: SHA-256 of the token only (`authz.password_setup_token`). Valid 72 h, once; a newer link closes any open one. Using it ends every other session of the user (as any new password does).
- Mail goes through the API mail port (SES from `PORTAL_FROM_EMAIL`, or the dev mailbox).
- Audit: `admin.user.password_invite` (`{ ttlHours }`), `auth.password_setup` (`{}`). No token or email.

## Staff sign-in and session (auth)

- **Session cookie** (audit F-14): over HTTPS (`PUBLIC_BASE_URL` https, or `NODE_ENV=production`) the cookie is `__Host-eureka_sid`: `Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, so a sibling subdomain cannot set or overwrite it. Plain-HTTP local development and tests keep `eureka_sid` without `Secure`. One definition (`SessionService.sessionCookieOptions()`) serves Google, dev and password sign-in and logout.
- **Transition (one release):** over HTTPS the API still reads the old `eureka_sid` cookie when `__Host-eureka_sid` is absent, so sessions issued before the rename survive the deploy; every new sign-in gets the new name and logout clears both. Remove the fallback (`SessionService.readSessionId`) in the release after.
- **Google callback failures** (`GET /api/auth/callback`, audit F-05) never answer with a problem JSON page: they `302` to `${PUBLIC_BASE_URL}/login?error=<code>` and log a `warn` with the code (no email). Codes: `expired` (no or expired sign-in state cookie), `cancelled` (the user cancelled at Google), `signin_failed` (state mismatch, code refused or replayed, invalid ID token, nonce mismatch), `unavailable` (Google's token endpoint timed out after 10 s, failed or answered 5xx), `domain` (account or email outside the company domain), `not_provisioned` (no active Eureka account; the `auth.denied` audit row is still written). Success: `302` to `PUBLIC_BASE_URL` with the session cookie.
- **Request id:** every response carries `x-request-id` (the X-Ray root of `x-amzn-trace-id` when present, else a UUID; a client `request-id` header is ignored) and every problem body carries the same value as `instance`. Quote it when reporting an error.
- **Retryable database conditions** answer `503` with `Retry-After: 1` (`detail` `query_timeout` for a statement timeout, `database_busy` when no connection is free within `DB_CONNECT_TIMEOUT_MS`, default 3000, or the database refuses connections) and `409` with a retry-safe `detail` for serialization failures, deadlocks and lock timeouts (the request was rolled back and can be sent again).
